Views and Templates (userprofile app / Profile model)

VIEWS IMPLEMENTED

1. profile_manual_view (FBV — HttpResponse, manual)
   URL: /profiles/manual/
   Purpose: Demonstrates building a response by hand — load the template
   object with loader.get_template(), render it to a string with a context
   dict, then wrap that string in HttpResponse() ourselves. Shows what
   render() is actually doing under the hood.

2. profile_render_view (FBV — render() shortcut)
   URL: /profiles/render/
   Purpose: Same query and same template as view 1, but uses Django's
   render() shortcut to combine "load template + fill context + wrap in
   HttpResponse" into a single call. Same output, less code.

3. ProfileBaseView (Base CBV — View)
   URL: /profiles/cbv-base/
   Purpose: Same logic as view 2, rewritten as a class inheriting from
   django.views.View, with the logic living inside a get() method instead
   of a bare function. Shows that a class-based view is not automatically
   "doing more" — it's the same manual query + render(), just organized
   differently, and .as_view() is what lets urls.py call it.

4. ProfileGenericDetailView (Generic CBV — DetailView)
   URL: /profiles/<pk>/detail/  (e.g. /profiles/3/detail/)
   Purpose: Shows a single profile's details. Unlike views 1-3, we never
   wrote a query or a render() call ourselves — DetailView automatically
   fetches the one object matching the pk in the URL (because model =
   Profile) and picks the template based on template_name, all we do is
   configure it.

5. ProfileGenericUpdateView (Generic CBV — UpdateView)
   URL: /profiles/<pk>/edit/  (e.g. /profiles/3/edit/)
   Purpose: Displays and processes an edit form for one profile. Django
   auto-generates the form fields from fields = ['bio', 'birthdate',
   'pronouns'], handles the GET (show form) and POST (save + validate)
   logic automatically, and redirects to get_success_url() after saving.


REFLECTION

HttpResponse (manual) vs render():
Writing profile_manual_view made it clear that render() isn't magic —
it's a shortcut for exactly the three steps I had to write out by hand:
get the template, render it with a context dict, wrap the string in
HttpResponse. In practice I'd always reach for render() day-to-day since
it's shorter and does the same thing, but building the manual version
first made render() actually make sense instead of feeling like a black
box. The manual version would only be worth using for something render()
can't do directly, like returning something other than HTML (e.g. our
section_counts_chart-style image response elsewhere in the project).

Base CBV (View) vs Generic CBV (DetailView/UpdateView):
The base CBV (ProfileBaseView) was barely different from the render()
FBV — same amount of code, just wrapped in a class with a get() method.
Where the generic CBVs actually saved real work was UpdateView: writing
a base View version of "show a form, validate it, save it, redirect" by
hand would have meant manually handling GET vs POST, building a form
class, validating input, and saving — UpdateView did all of that from
four lines of configuration (model, fields, template_name,
get_success_url). I'd reach for a base View when the logic is genuinely
custom/one-off, and a generic CBV whenever the task matches a common
pattern (list, detail, create, update, delete) that Django already
solved.
